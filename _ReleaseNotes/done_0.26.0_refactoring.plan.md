# v0.26.0系: 出欠画面リファクタリング計画（plan）

## 目的

- 主日集会・祈りの集会の出欠画面にある複雑化した実装を整理し、機能追加時の変更コストと不具合リスクを下げる。
- 直近で追加した「オンライン / 他地方 列の表示設定」を、重複の少ない構造で維持できる状態にする。

## 対象範囲

- 主対象:
  - `src/app/(dashboard)/attendance/lordsday/SundayAttendance.tsx`
  - `src/app/(dashboard)/attendance/prayer/PrayerMeetingAttendance.tsx`
  - `src/contexts/DisplaySettingsContext.tsx`
  - `src/app/(dashboard)/settings/DisplaySettingsSection.tsx`
- 非対象:
  - DB スキーマ変更
  - 既存の出欠データ構造（`is_online`, `is_away`）の意味変更

## 現状課題（要約）

- `SundayAttendance.tsx` が巨大（2,000行超）で、状態管理・データ取得・集計・UI が1ファイルに集中。
- PCテーブル表示とスマホカード表示で同系ロジックが重複し、変更漏れのリスクが高い。
- 表示設定の項目追加時に `localStorage key + state + setter` が都度増える構造でスケールしにくい。
- 主日と祈りの集会で似た実装が並行し、将来の仕様差分で乖離しやすい。

## 方針

- 一気に共通化せず、**小さく分割して安全に進める**。
- まず主日画面で責務分離し、安定後に祈りの集会へ水平展開する。
- 画面挙動は変えず、内部構造の改善を優先する（UI/UXの意図変更は別チケット）。

## 実行フェーズ

### フェーズ1: 表示設定基盤の整理

- `DisplaySettingsContext` を「設定定義 + 汎用 read/write」に寄せる。
- `fullWidth / showLordsDayOnlineColumn / showLordsDayAwayColumn` を同じ管理パターンに統一。
- `DisplaySettingsSection` 側も設定定義を元に描画できる形を検討（最低限、追加コストの低い構造へ）。

完了条件:
- 設定項目追加時に、重複実装が最小限になる。
- 既存設定値の読み書き挙動が維持される。

### フェーズ2: 主日画面の列構成ロジック抽出

- `オンライン / 他地方` の列表示条件、ヘッダー文言、列数計算（`colSpan`）を1箇所で算出する。
- Desktop / Mobile で共有できる「列定義（column config）」を導入する。

完了条件:
- 表示列ON/OFFに関する条件分岐が散在しない。
- DesktopとMobileで列不整合が起きない。

### フェーズ3: 主日画面の責務分離

- データ操作ロジックを `useSundayAttendanceController` 的なフックへ分離。
- 表示は少なくとも以下へ分割:
  - Desktopテーブル部分
  - Mobileカード部分
  - 共通のメンバー行レンダリング補助

完了条件:
- `SundayAttendance.tsx` が「画面オーケストレーション」中心になり、可読性が上がる。
- 主要ユースケース（閲覧・編集・保存・検索）が挙動維持。

### フェーズ4: 祈りの集会への適用

- 主日で確立したパターン（列定義、行UI補助、設定参照）を `PrayerMeetingAttendance` に適用。
- 必要な差分（主日固有の「他地方」仕様など）は分岐で維持。

完了条件:
- 祈りの集会側の重複を削減し、主日との構造差が説明可能な範囲に収まる。

### フェーズ5: 検証・仕上げ

- `npx tsc --noEmit` を通す。
- 手動確認:
  - 表示設定トグル（オンライン/他地方）
  - 編集モードの切替
  - 出欠・オンライン・他地方・メモ保存
  - グルーピング表示
  - スマホ表示崩れがないこと

完了条件:
- 型エラーなし
- 既知挙動の後退なし

## リスクと対策

- リスク: UI分割時の props 受け渡し漏れ
  - 対策: 先に型（Props）を明示し、段階的に差し替える。
- リスク: Desktop/Mobile の表示差分増加
  - 対策: 列定義を共通化し、両方で同じ定義を参照する。
- リスク: 変更量が大きくレビュー負荷が上がる
  - 対策: フェーズ単位で小さくコミットし、各段階で動作確認を入れる。

## 進行順（推奨）

1. フェーズ1（設定基盤）
2. フェーズ2（主日の列定義）
3. フェーズ3（主日の責務分離）
4. フェーズ4（祈りへ展開）
5. フェーズ5（検証）
